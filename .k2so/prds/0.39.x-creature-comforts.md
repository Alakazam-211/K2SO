## tl;dr

After the 0.39.0 public release (post-Phase-2.5d), the workweek shifts focus from architecture cleanup to user-facing polish. Six items requested by users, ranging from small UI defaults to harder reliability work. No new architectural primitives — each item is a focused fix or feature on the now-stable 0.39.0 foundation.

The 0.39.x cycle is explicitly NOT the 0.40.0 cycle (Phase 2.6 + Phase 3 — tunnel decision + contract hardening). Those resume after the workweek when the team has bandwidth for the bigger architectural moves.

## Items (6)

### 1. Custom agents no longer pinned by default — **small**

**User pain**: When a user picks Custom Agent mode for a workspace, K2SO auto-pins the agent's chat in the tab bar. Some users don't want that pin — it clutters the tab bar with chats they're not actively using.

**Scope**:
- Change the default behavior in workspace creation / agent-mode-switch flow so Custom Agent doesn't auto-pin a chat
- User can still manually pin from the tab bar context menu / Settings
- Existing workspaces with already-pinned Custom Agent chats stay pinned (no migration to unpin)

**Implementation surface**:
- Likely in `crates/k2so-core/src/agents/commands.rs::create` (or wherever agent-mode-set logic lives — post-Phase-2.5d this moves to `workspace/agent.rs`)
- Or in the React layer where the tab bar's pinned-chat list is initialized for new workspaces
- One-line behavior change + maybe a settings flag if we want it user-toggleable

**Tests**:
- Create a new workspace in Custom Agent mode; verify no pinned chat is auto-created
- Existing workspaces: open a workspace that had a Custom Agent + pinned chat pre-upgrade; verify the pin persists

**Out of scope**: changing default pinning behavior for OTHER agent modes (K2SO Agent, Workspace Manager). This item is custom-only.

### 2. Option to pin HTML files to be rendered — **medium**

**User pain**: Users want to pin HTML files (dashboards, generated reports, documentation) in their workspace and have K2SO render them inline rather than just showing the source.

**Scope**:
- Add ability to pin an HTML file from the file tree (right-click → "Pin as rendered HTML")
- Pinned HTML files render as an iframe or sandboxed webview in the tab bar
- File watcher updates the rendered view when the source HTML changes
- User can unpin via context menu
- Persistence: pinned HTML files stored in workspace settings (per-workspace list)

**Implementation surface**:
- New tab type in renderer: `PinnedHtmlPane`
- File watcher subscription in the daemon (or use existing fs watcher infrastructure)
- Storage: probably extend `workspace_tab_sessions` table or add a `pinned_html_files` column to `projects`
- New Tauri command: `pin_html_file(project_path, file_path)` + `unpin_html_file(...)`
- Sandboxing: iframe with `sandbox="allow-scripts"` minimum; consider whether to allow same-origin, network, etc.

**Tests**:
- Pin a simple `<h1>Hello</h1>` file → verify it renders
- Edit the file externally → verify the rendered view updates
- Unpin → verify it's removed from the tab bar
- Restart the app → verify pinned HTML survives restart

**Security note**: rendering arbitrary HTML from the workspace is a real attack surface. Document the threat model + use a sandboxed iframe. Don't allow privileged Tauri APIs from the iframe content.

**Out of scope**: rendering Markdown, PDF, or other non-HTML formats (those already have viewers); arbitrary URL pinning (only local file paths).

### 3. Pinned chat + pinned inbox shown by default even when agent mode is off — **small**

**User pain**: When a workspace has `agent_mode = 'off'`, the pinned chat tab and pinned inbox tab might be hidden. Users want quick access to those regardless of agent mode — even an "off" workspace can have prior chat history they want to reference + an inbox that might have items from other workspaces (cross-workspace `msg --inbox` delivery).

**Scope**:
- Pinned chat tab: render at the top of the tab bar even when `agent_mode === 'off'`. Clicking spawns a fresh Claude session (or whatever the workspace's default agent CLI tool is) if no session exists; otherwise resumes.
- Pinned inbox tab: render at the top of the tab bar even when `agent_mode === 'off'`. Shows whatever's in `.k2so/inbox/`.
- This DIFFERS from Phase 2.5b's Skills section work — that was the Settings page rendering Skills regardless of mode. This is the tab bar rendering pinned chat + inbox regardless of mode.

**Implementation surface**:
- React layer: the `TabBar.tsx` component (or whatever renders the tab bar)
- Likely a conditional render that currently includes `agentMode !== 'off'` — relax it
- Probably need to update `tabs.ts` store's initialization logic too

**Tests**:
- Set a workspace to `agent_mode: off` → verify pinned chat + pinned inbox tabs visible
- Click pinned chat → verify Claude (or default agent) spawns
- Click pinned inbox → verify inbox renders with content
- Switch to other modes → verify behavior stays consistent

**Out of scope**: changing the OTHER tabs that are mode-gated (the workspace manager block in Settings, etc.). This is tab-bar specific.

### 4. Terminal session resilience + dormancy notifications — **hard**

**User pain**: Active Cmd+T terminal sessions can get into bad states (PTY hang, network/SSH timeout, agent goes idle for too long). Users want:
- Better resilience so sessions don't die unnecessarily
- Notifications when a session has gone dormant (no output / no activity for X minutes)

**Scope** (split into sub-items):

**4a. Resilience for active terminal sessions**:
- Audit current PTY lifecycle in `crates/k2so-core/src/terminal/daemon_pty.rs` and the v2 session map (`crates/k2so-daemon/src/v2_session_map.rs`)
- Identify failure modes: PTY EOF, signal interrupts, daemon restart, network disconnect, OOM
- Add reconnect / restart logic where appropriate (today's `keepDaemonOnQuit` covers the Tauri-quit case; need broader coverage)
- Surface failure types to the renderer so the UI can offer "Reconnect" / "Restart this session" affordances

**4b. Notifications on dormant sessions**:
- Track "last output" or "last user input" timestamp per active terminal session
- Configurable threshold (default: 30 min? 1 hour? per-user setting)
- When threshold exceeded, emit a notification:
  - Desktop notification (via Tauri's notification API)
  - UI badge / indicator on the dormant tab
- User can dismiss / configure threshold / disable per-session

**Implementation surface**:
- Daemon-side: add idle-time tracking to v2 session map; add a daemon-events emit for "session dormant" when threshold crossed
- Renderer: subscribe to dormant events; show notification + tab badge
- Settings: new section for "Idle timeout" / "Dormancy notifications" preferences

**Tests**:
- Spawn a terminal, run `sleep 3600`, verify no dormancy notification within the active window
- Spawn a terminal, leave idle for X+1 minutes (mock the timer), verify notification fires
- Force-kill a PTY process; verify the resilience layer offers a reconnect path

**Why hard**: PTY lifecycle is the architectural keystone (per the Phase 2.5 smoke checklist Unit 3 — "Terminal PTY survives Tauri quit" was the critical test). Touching this code carries regression risk. Plus the cross-cutting notification system is real work.

**Out of scope**: SSH-specific reconnect logic (treat SSH sessions like any other terminal); auto-restart of crashed processes (only the PTY itself, not what's running inside it).

### 5. Make the canonical AGENT.md feature optional — **medium, but lots of thinking**

**User pain**: K2SO writes a canonical AGENT.md (or SKILL.md post-Phase-2.1) into each workspace's `.k2so/` tree, regenerates it on every wake, and fans it out to harness-discovery files (`./CLAUDE.md`, `./AGENTS.md`, `./AGENTS.md`, `./.cursor/rules/`, `./.gemini/...`, etc.). The auto-regen + harness fan-out workflow is intimidating to new users — they see K2SO writing files into their workspace and worry about overwriting their existing instructions, conflicts with `.gitignore`, or the magic of "what is K2SO doing?"

**Scope** (heavy on design):

This needs a **design conversation** before implementation. Key questions:
- Should the auto-regen be **opt-in** (new workspaces default to OFF; user enables in Settings if they want it) OR **opt-out** (default ON; user disables if they don't want it)?
- If opt-in, what fallback context does the agent get if there's no SKILL.md? (Probably just the workspace name + `PROJECT.md` if present.)
- Should the harness fan-out be **separately togglable** from the SKILL.md regen itself? (User might want SKILL.md generated but NOT fanned out to CLAUDE.md / AGENTS.md / etc.)
- What's the UX for surfacing "your workspace has these files; K2SO can manage them — do you want to?" — a first-launch wizard? A Settings panel? Both?
- If the user disables K2SO's SKILL.md management, what happens to existing managed files? (Trash them via safe_delete? Leave them?)

**Implementation surface (after design)**:
- New per-workspace setting: `skill_md_managed: bool` (and probably `harness_fanout_enabled: bool`)
- Conditionalize the regen calls in `workspace/skill_writer.rs` (post-Phase-2.5d) based on the setting
- UI: new section in workspace settings + onboarding step
- Migration: existing workspaces default to current behavior (managed = true) so we don't break anyone

**Tests**:
- Disable `skill_md_managed` → verify SKILL.md regen doesn't fire
- Disable `harness_fanout_enabled` while keeping skill_md_managed → verify SKILL.md still written but CLAUDE.md etc. NOT fanned out
- Re-enable → verify files get regenerated next wake

**Why "lots of thinking"**: the SKILL.md / canonical AGENT.md system is core to how K2SO bridges to CLI LLM tools. Making it optional changes how users interact with the product. Need to think through how the agent operates when SKILL.md is absent, what UX surfaces the choice clearly, and how to gracefully handle the off state.

**Out of scope**: removing the SKILL.md system entirely (only making it optional); changing what GOES INTO SKILL.md when it IS enabled.

### 6. Verify K2SO works well without git enabled per workspace — **untested**

**User pain**: K2SO assumes workspaces have git initialized. Some users want to use K2SO with non-git directories (e.g., a documentation folder, a project that uses Mercurial, or a directory that's intentionally not version-controlled).

**Scope**:
- **Investigation first** (likely a research subagent pass):
  - Grep daemon + core for `git2` / `Repository::open` / `git status` / `is_git_repo` calls
  - Identify which code paths assume a git repo exists
  - List which features actually need git (worktrees, commit, diff) vs which don't (terminal, inbox, skills, heartbeats, etc.)
- **Then implementation**:
  - Gracefully handle "not a git repo" — operations that need git should error with a clear message; operations that don't need git should work as if git wasn't a concept
  - Settings UI / onboarding: detect that a workspace isn't git-initialized and either offer "Initialize git here" OR set per-workspace flag "non-git workspace"
  - Worktree-related features (delegate, review queue) need to gracefully no-op or be hidden when git is absent

**Implementation surface**:
- `crates/k2so-core/src/git/` or wherever git operations live
- Settings: per-workspace `git_enabled: bool` (or detect from filesystem)
- UI: hide / disable git-dependent affordances in non-git workspaces

**Tests**:
- Create a workspace in a non-git directory → verify K2SO works for the non-git features
- Try to use a git-dependent feature (worktrees, commit) → verify clear error message
- Initialize git in that workspace → verify K2SO picks it up + git features become available

**Why "never tested"**: K2SO has always been used in git workspaces. No one knows how many code paths assume git. The investigation will reveal scope.

**Out of scope**: supporting Mercurial / SVN / other VCS specifically; this is just about gracefully handling "no VCS at all."

## Suggested sequencing

The items aren't strictly sequential. Recommended order based on size and dependency:

```
Day 1-2 (start with small wins):
  - Item 1: Custom agents no longer pinned by default
  - Item 3: Pinned chat + inbox visible when agent mode is off
  - Item 6 investigation (research subagent to map git dependencies)

Day 2-3 (medium items):
  - Item 5 design conversation (user + pod-leader decide questions)
  - Item 5 implementation (after design)
  - Item 6 implementation (after investigation; scope clarifies)
  - Item 2: Pin HTML files (parallelizable with 5/6)

Day 4-5 (hard item):
  - Item 4a: Terminal session resilience
  - Item 4b: Dormancy notifications
  - Final smoke pass on 0.39.x cumulative changes
```

Items can ship individually (0.39.1, 0.39.2, etc.) or batch into 0.39.5 if multiple complete together.
