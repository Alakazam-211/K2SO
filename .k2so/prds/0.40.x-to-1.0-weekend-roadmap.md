# 0.40.x → 1.0.0 Weekend-Cycle Roadmap

**Status**: Drafted 2026-05-25 — user direction for 4 weekend cycles + interleaved workweek polish.
**Owner**: Rosson + pod-leader
**Cadence**: each cycle = one weekend (critical-path `.0` ship) + the following workweek (`.X` polish + additional items)
**Total scope**: ~4 weeks (4 weekend cycles + 3 workweeks) from 0.40.0 ship to 1.0.0 launch
**Replaces**: the original "Phase 2.6 → Phase 3 → Phase 4" sequencing from `secure-tunnel-monetization-roadmap.md`. The 4-cycle plan reorganizes that work into weekend-shipping milestones.

---

## tl;dr

After 0.39.x (creature comforts workweek), K2SO renames to **K2** at the 0.40.0 ship. Each weekend ships a `.0` critical-path milestone; the following workweek ships `.X` polish items. The arc:

- **0.40.0** (Weekend 0): K2SO → K2 rebrand + monetization launch (K2 Companion + K2 Connect)
- **0.40.X** (Workweek 0): Hermes support, port-3000 publishing, HTML dashboard, script system
- **0.41.0** (Weekend 1): Brain/Documentation System
- **0.41.X** (Workweek 1): research folder jailing (silo'd agents), Brain polish
- **0.42.0** (Weekend 2): TTS summaries + Kessel v2 jsonl renderer
- **0.42.X** (Workweek 2): Mobile TTS, Kessel polish, Changes tab cleanup, dormant-session notifications across renderers
- **1.0.0** (Weekend 3): K2 graduates — Owner/Manager grouping + Alakazam Engine SKILLs + advertisement

---

## ⚠️ Critical prerequisite: K2 trademark Class 9 + 42 search

**Before 0.40.0 ships publicly with the K2 name**, a USPTO TESS search across Class 9 (computer software) and Class 42 (SaaS) MUST be completed. Initial scan found K2 Advisors L.L.C. holds K2 in Class 36 (financial services) which does NOT block — but the software-class space hasn't been verified. Strongly recommend a 30-min trademark attorney consult before committing money to marketing materials, app store listings, and the .app bundle ID rename.

If software-class trademark IS blocked: a fallback name decision is needed before 0.40.0. Don't ship the rename in 0.40.0 if trademark posture isn't cleared.

## 0.40.x — Weekend 0 cycle (K2 launch + monetization)

### 0.40.0 critical path (ships at Weekend 0)

#### Item 0.40.0.A — Software rename: K2SO → K2

**Scope**:
- All product copy: app name in `tauri.conf.json`, Info.plist, About dialog, Settings UI, generated SKILL.md, release notes, documentation, README, website
- CLI tool: `k2so` command renamed to `k2` (alias for one release cycle, then deprecated)
- Bundle ID: `com.alakazam.k2so` → `com.alakazam.k2` (CAUTION: this breaks existing launchd plists, settings paths, file associations. Plan a migration step that preserves user state.)
- Daemon binary: `k2so-daemon` → `k2-daemon` (per Phase 2 the daemon is sidecar; rename + back-compat symlink for one release)
- File paths: `~/.k2so/` stays as the data directory (don't migrate user data on rename); document that the prefix is historical
- Crate names: `k2so-core` → `k2-core`, `k2so-daemon` → `k2-daemon` (cargo workspace rename — substantial)
- Generated SKILL.md / harness fanout: regenerated content references "K2" not "K2SO"

**Complexity**: Large. Touches every product surface.

**Implementation strategy**: phased — do the user-visible names (UI, CLI alias) first, then bundle ID + crate names (which require careful migration), then internal cleanup.

**Pre-requisite gates**:
1. Trademark Class 9 + 42 cleared
2. `k2.dev` DNS pointed at production infrastructure (or kept as a future-pointer)
3. Bundle ID migration plan reviewed (preserves `~/.k2so/` state, launchd plist transitions cleanly)

#### Item 0.40.0.B — K2 Companion working (Phase 3 deliverable)

**Scope**: ship the rebuilt Mobile Companion protocol from Phase 3 Workstream D. Includes:
- WebSocket-first contract (replaces the older HTTP polling)
- CompactLine terminal grid streaming
- Pairing flow against the K2SO Hosted tier OR Free Tailscale tier OR BYO tunnel
- iOS / Android client updates (separate apps; submission cycles may extend beyond 0.40.0 — phase the desktop side from the mobile-app-store side)

**Dependencies**:
- Phase 2.6 tunnel decision must land (Workstream B blocks on it)
- Phase 3 Workstream A (typed router), C (OpenAPI), D (Mobile contract) must be complete

**Effort**: substantial multi-week work compressed into the 0.40.0 weekend. **Realistic check**: this may slip to 0.40.X if Phase 3 Workstream B isn't fully baked by Weekend 0. Plan accordingly.

---

#### Item 0.40.0.C — K2 Connect working

**Scope**: ship the desktop-to-desktop remote K2 workspace access feature (Phase 3 Workstream E):
- A user can run K2 on Machine A (e.g. home desktop) and access it from Machine B (e.g. laptop on the road)
- Reuses the same tunnel infrastructure as Companion
- Frontend: connection list / address book (per Phase 2.6 PRD's `ConnectHost` schema)
- Auth: K2 bearer-token (same as Companion)

**Dependencies**: same as Companion — Phase 3 B + C + E.

**Note**: K2 Connect was previously framed as a sibling of K2 Companion. They share infrastructure (TLS, auth, tunnel) but have different UX (mobile pairing screen vs desktop connection picker).

---

#### Items 0.40.0.D — Monetization plumbing

**Scope** (Phase 4 work compressed into 0.40.0):
- Stripe webhook integration for subscription lifecycle
- Per-user subdomain provisioning on the chosen tunnel backbone
- Admin UI for monitoring + manual interventions
- Signup flow: user pays → control plane provisions tunnel → credentials delivered to daemon → ready

**Realistic check**: this is the most aggressive part of the 0.40.0 plan. Phase 4 originally estimated 2-3 engineer-weeks. Compressing into a weekend means high risk. If monetization can't ship at 0.40.0, slip it to 0.40.X — the rename + Companion + Connect can ship without billing first.

## 0.41.x — Weekend 1 cycle (Brain/Documentation System)

### 0.41.0 critical path

#### Item 0.41.0.A — Brain / Documentation System

**Scope**: a documentation system for workspaces (and maybe across workspaces) that the agent can navigate intelligently. The "brain" metaphor suggests:
- Structured knowledge persisted across sessions
- Agent can read prior decisions, conclusions, design notes
- Agent can write new content into it (not just read)
- Searchable / browseable from the UI

**Open design questions** (substantial):
- Storage: filesystem markdown files (like `.k2so/notes/` or `.k2so/docs/`)? Or a DB table? Or both?
- Schema: free-form markdown OR structured (decision logs, design docs, FAQ, etc.)?
- Cross-workspace: each workspace's brain is independent, or there's a shared "user brain" too?
- Agent interaction: how does the agent decide WHEN to read brain content vs ignore? (Skill-like loading from #7 of 0.39.x?)
- Integration with existing `.k2so/notes/` (which K2 already creates per Phase 2.5d's `agents/workspace.rs` audit)?

**This needs a design PRD** before implementation. Probably its own audit pass + design conversation.

### 0.41.X workweek items

#### Item 0.41.X.1 — Research folder jailing (silo'd agents) — BETA

**Scope**: a way to constrain agent activity to a specific "research" sub-folder of the workspace, so the agent can't accidentally write outside it. Useful when a user wants to:
- Let the agent freely explore + write notes / experiments
- But not touch production code or other workspace areas

**Implementation surface**:
- Per-workspace setting: `research_folder: Option<String>` — when set, agent operations are constrained
- Filesystem access guardrails: K2 daemon refuses writes outside the research folder when this mode is active
- UI affordance: "Research Mode" toggle that lets users carve out a sandbox

**Why beta**: this is a security/sandboxing feature. Real attackers won't be stopped by it (agent can probably escape via shell commands), but it's a safety net for accidental damage. Document the trust model clearly.

## 0.42.x — Weekend 2 cycle (TTS + Kessel renderer)

### 0.42.0 critical path

#### Item 0.42.0.A — TTS summaries of what AI finished + Kessel v2 jsonl stream renderer

**Two coupled features**:

**TTS summaries**: when an agent completes a task / checkin / heartbeat, K2 generates a short text-to-speech summary. Useful for users who step away and want an audio status update on return ("agent completed PRD draft, no errors, ready for review").

**Kessel v2 jsonl renderer**: revival of Kessel concepts. Kessel was originally an alternative terminal renderer (the "session stream" path) that got mostly retired in 0.39.0 cleanup. v2 brings it back as a JSONL-stream-based chat renderer — agents emit structured JSONL events; renderer parses + displays beyond raw PTY output. Better than Alacritty for chat-style interactions; preserves Alacritty for genuine terminal sessions.

**Open design questions**:
- TTS engine: native macOS `say` command? Cloud API (ElevenLabs, OpenAI TTS)? User-configurable?
- Kessel v2 protocol: what JSONL schema? Map onto existing agent events?
- Rendering: HTML + CSS like a normal chat UI? Custom Tauri component?
- Toggleable per workspace? Per tab?

**Why coupled**: TTS summaries need structured "task completed" events from the agent — those come naturally out of a JSONL stream protocol. Kessel v2's JSONL renderer surfaces those events; TTS reads them. Implementing them together is more efficient than separate passes.

**Memory pointer**: see `reference_kessel_*` memories for Kessel history (originally a T0 SessionStreamSession, archived to `kessel-research-archive.md` PRD during Phase 1).

**Scope**: K2 launches as a v1.0 product:

#### Item 1.0.0.B — Simplified Owner/Manager Agent Grouping

**Scope**: a UX/conceptual simplification for users who delegate work to multiple K2 instances. Today K2 has "workspace manager mode" + various sub-agent patterns. The simplification likely:
- Owner = the user (you)
- Manager = a workspace that orchestrates others
- (Possibly a third tier — Worker / Specialist agents)
- UI surfaces this hierarchy clearly in the sidebar / Settings

**Open design questions**:
- Is this purely UX renaming, or does it change underlying data model?
- How does it interact with the Phase 2.1 workspace==agent invariant (every workspace has exactly one primary agent)?

**This needs design** — probably an audit pass after 0.42.x to understand the current owner/manager surface before simplifying.

---

#### Item 1.0.0.C — Owner / Manager K2 SKILLs for Alakazam Engine + software auto-builds

**Scope**: ship K2 SKILLs (per 0.39.x item #7) that enable:
- **Alakazam Engine integration**: K2 agents can interact with Alakazam Labs' product infrastructure (more context needed on what this means)
- **Software auto-builds**: a SKILL that teaches K2 how to autonomously build, test, deploy software projects

**Open questions** (substantial):
- What is the Alakazam Engine? — internal Alakazam Labs platform? — third-party integration?
- "Software auto-builds" scope — CI/CD pipeline orchestration? Generative coding assistant? Both?
- Are these SKILLs shipped publicly (any user can install) or private (only Alakazam Labs personnel)?

**This needs a design conversation** — the SKILLs themselves are content authoring; the question is what behaviors they unlock.
